## Auth and device binding (issues #44, #45)

- **Sign-in:** `POST {CONVEX_SITE_URL}/api/auth/sign-in/email` `{email,password}` with **no Origin header**. Prefer the `set-auth-token` response header when present; otherwise use the top-level JSON body `token` (as verified on DEV, where the header is absent). Reject missing, malformed or whitespace-containing session tokens. OkHttp retains no `Set-Cookie` cookies; only the validated token is stored in the encrypted session vault. 400/401 → "Incorrect email or password"; 403 → refused; 429 → rate limited; IO failure → offline; other codes → server error. The password is never stored or logged. The password field is plain `remember`, so it stays out of saved instance state.
- **Session at rest:** `auth/SessionVault.kt` encrypts the session with an AES-256-GCM AndroidKeyStore key (fresh IV per write, fixed AAD). Only IV and ciphertext go to `SharedPreferences`. If the ciphertext fails to decrypt (tamper, lost key, restore onto another device), the app treats it as signed out and wipes it. `allowBackup=false`, and the backup and data-extraction rules exclude all app data. EncryptedSharedPreferences (deprecated) is not used.
- **Convex JWT:** `GET /api/auth/convex/token` with the session bearer. The JWT is held in memory only and refreshed 60 s before its `exp`. A Convex function 401 triggers exactly one refresh and retry. A 401/403 on the token exchange ends the session.
- **Sign-out:** `POST /api/auth/sign-out` with the session bearer (best effort). The local session, JWT and cached deviceId are always wiped. The device key is kept because it is the admin-registered key.
- **Device key:** `device/KeystoreDeviceSigner.kt` uses EC P-256, `PURPOSE_SIGN`, SHA-256. It is StrongBox-backed when `FEATURE_STRONGBOX_KEYSTORE` is present, otherwise TEE; the emulator reports Software. The protection level appears on the enrollment screen and is sent as unverified `attestation.keyId`. The public key is `publicKey.encoded` (DER SPKI) in base64. `EcdsaEncoding` converts JCA DER to 64-byte P1363 using strict DER parsing (short-form lengths, minimal positive INTEGERs, 0 < r,s < n, no trailing bytes).
- **Enrollment:** `mobile/devices:mine {publicKey, app:"ANDROID"}` → `null` shows "This phone isn't registered yet" with the copyable key, fingerprint and model/OS/app version, a **Check again** button and a 10 s auto-poll. Active and unbound → `challenge` → sign `BIND|deviceId|credentialId|nonce|timestamp` → `bind` → read back via `mine` → "Phone ready". Revoked or suspended → "This phone was removed — ask your admin". The bind timestamp is derived from the challenge's server `expiresAt − 60 s`, so phone clock skew can't break the ±60 s window. The deviceId is persisted (non-secret) and re-verified on every launch.
- **DEV public-key file:** the `devDebug` build writes the **public** key only to `/sdcard/Android/data/com.sunpride.field.dev/files/device-public-key.txt` on first launch, even before sign-in or URL configuration. Pull it with `adb pull` and pass it to `packages/backend/scripts/register_device.ts --public-key-file`.

Tests: JVM (`app/src/test`) covers MockWebServer sign-in/token/sign-out/401-retry, Convex envelopes, the enrollment state machine, redaction, and DER↔P1363 plus signer checks against `packages/domain-contracts/fixtures/mobile-v1/crypto/request-proof.json`, which is read in place through a test-resources `srcDir` rather than copied. Instrumented (`app/src/androidTest`) covers Keystore key persistence and sign/verify, StrongBox when the device has it, the encrypted vault round-trip, tamper handling and wipe, and the Compose sign-in/enrollment states.

## Visit-only local store (issue #46)

`storage/FieldStore.kt` exposes `EncryptedFieldDatabase.open(context)` and `RoomFieldStore(db, StoreScope(fullAuthSubject, registeredDeviceId, scopeFingerprint))`. The caller must construct `StoreScope` from an authenticated/bound identity, never from an arbitrary UI selection. SQLCipher for Android **4.12.0**, Room **2.7.2**, AndroidX SQLite **2.7.0** are pinned in `gradle/libs.versions.toml`; `SupportOpenHelperFactory` is mandatory. A random 32-byte install passphrase (ASCII-hex encoded for SQLCipher) is AES-256-GCM wrapped with an independent Android Keystore key; only IV+ciphertext are saved in private preferences. A missing/corrupt key does not fall back to plaintext or erase the database. The app manifest disables backup; both `backup_rules.xml` and `data_extraction_rules.xml` exclude the entire database, file and shared-preference domains (cloud and device transfer). The exported v1 Room schema remains a migration baseline; v2 adds scoped deltas, v3 adds last-sync time, and v4 adds snapshot list position through explicit non-destructive migrations. Sequence remains in each immutable bootstrap JSON row; list position preserves response order when sequence is absent. `MigrationTestHelper` validates all exports and the full v1 → v4 chain. Never use destructive migration fallback.

The repository surface for slices I/K is deliberately small:

- `stage(ScopedSnapshot)` stages a complete assembled bootstrap (employee, route, planned visits, outlets, linked customers, tasks) in a new generation; `swap(generation, finalCursor, leaseExpiresAt, cacheExpiresAt)` atomically promotes it and discards only old **snapshot** rows. Never call swap on a nonfinal page. Readers `todaysVisits(ManilaDay)` and `outlets()` see only the active generation. There is no catalog, price, order, collection or stock cache; server visit/activity deltas are a later slice.
- `enqueue(IntentRow, now)` transactionally inserts an immutable exact serialized visit operation and ordered outbox row; request IDs and client visit IDs are stable UUIDs supplied by the sync layer. `pending()` returns those original bytes in createdAt/requestId order. `recordAck` inserts the server ack **before** marking done in one transaction; `recordRejection` freezes an item for review without destroying its intent. No implicit retry of review items. Duplicate IDs abort rather than mutate a payload.
- `cursor()`/`setCursor(null)` retain pending work; `isLeaseValid(now)` requires a promoted snapshot and `now < offlineLeaseExpiresAt`. Expired caches remain readable as stale, but new intents fail. `syncHealth()`/`setSyncHealth()` are persistent metadata. `holdForReview()` is the sign-out/revoke/scope-change hook: clears the cursor, blocks new intents and keeps unsent work; an explicit supervised recovery workflow is still needed. Do not wipe the DB/passphrase from the existing session-vault sign-out path. Revocation while disconnected cannot be detected immediately; never label cached data live.

The live auth backend invokes `EncryptedFieldDatabase.holdExisting` before sign-out and on removed/unregistered device or expired session, preserving unsent work across credential loss. Verified same-account bootstrap now reactivates only its bound device/scope partition atomically with snapshot promotion; supervised recovery for rejected items remains future work. Instrumented tests on emulator and phone exercise persistence, ciphertext absence/wrong key, transaction rollback, snapshot swap, ack ordering, isolation, lease, hold and activity recreation. Offline access ends at the server-provided next 22:00 Asia/Manila close. Queued work says “Sync before 10 PM” until its service-day close, then “Late · held for review”; explicit held/needs-review states take precedence.

## Today dashboard (SP-0066 / AND-009)

`ui/today/TodaySummary.kt` is a pure projection over the cached plan and local outbox; `ui/today/TodayDashboard.kt` renders it. Today shows, top to bottom: **Calls** (finished of planned, a progress bar, and productive calls of finished with a percentage, rounded down like the server). A finished call is productive by the governed rule mirrored in `storage/ProductiveCall.kt` from `sfa/productive_call.ts`: any one listed activity recorded at the visit (order, merchandising or price check, inventory check), never the End call outcome alone; a truck seller's merchandising counts only with the `no_sales_due_to_inventory` reason. The seller's rule comes from the daily sales report; until one is fetched the phone applies the stricter truck-seller rule so it never over-claims, **Current call / Next store** (the open call, else the first unfinished stop in plan order, with “Stop N of M”; tapping opens the visit in DEV builds), **Route** (route code from the bootstrap `route.code` and every stop numbered in MCP order with its status, outcome and time spent), and **Sales** (target today, sold today with percent, month to date against the monthly target) from the seller's own daily sales report `dsr/report:day`, read on each sync and saved encrypted for the day; offline it shows the saved copy with its time, a refusal shows nothing, and with no copy it says “Sync to see sales” instead of zeros. The planned stops are the day's call list. Sync state stays in the pinned top-bar label (tap for details), not duplicated in the dashboard.

## Bootstrap and Today (issue #47)

`sync/BootstrapClient.kt` obtains a new authenticated device challenge for every POST attempt (including the single JWT 401 refresh), derives timestamp from the challenge expiry, hashes the exact UTF-8 body it sends, and signs via `RequestSigner`. It follows bounded page cursors, validates v1 responses, assembles all pages before staging, and promotes snapshot/cursor/lease in one Room transaction. A held partition is released **only** by a verified bootstrap for the same full subject/device/scope during that promotion; the other account's rows remain isolated. The Today screen reads Manila-today visits from SQLCipher and displays the last sync, stale/offline or update-required state, and manual Sync now. On an offline relaunch a still-present encrypted session can reopen its cached partition, but is labeled pending until online enrollment succeeds. No live DEV identity/bootstrap was exercised in this slice.

**Wire discrepancy:** frozen `error-*.json` fixtures contain nested `error: {code,message,retryable}`, but the current `mobile/http_handlers.ts` sends these fields flat. The decoder handles both and never displays server messages. The HTTP authorizer returns 401 for revoked devices instead of `device_revoked`; the app attempts an authenticated `mine` read to distinguish removal and hold work. If offline, revocation cannot be known immediately. The TypeScript fake client uses `Date.now()` for signed timestamps; Android derives the server time basis from challenge expiry to tolerate phone clock skew. The schema's strict full-envelope parser rejects unknown enum values while the compatibility policy specifies raw unknown preservation; the Android response-status helper keeps raw unknown values without treating them as accepted.

If there is no visit today, record the empty state rather than changing the phone clock or forging a visit. Airplane mode after a successful bootstrap, relaunch and confirm cached visits are marked stale/pending; reconnect and retry. An already registered device for another profile must be revoked/reconciled first; do not self-register. Afterwards sign out and remove only `com.sunpride.field.dev` if the phone is shared.

## DEV visit diagnostic and delta (issues #48, #49)

The DEV build adds a visit action to a Today planned row and an unplanned action for cached outlets (requires a nonblank reason). Use **Start** on arrival and **End call** after recording completed/nonproductive productivity (nonproductive requires a reason code). Capture foreground location on both actions; denied/failed/timed-out fixes become explicit `location: null` and never block the call. No distance or accuracy gate is applied on the phone. MCP sequence (or original bootstrap list order when absent) and one-open-call-per-service-day are enforced by typed controller rules and again inside the Room enqueue transaction. Queued or accepted End unlocks the next store; rejected End does not. Local Start/End device times produce time spent. Captured fix accuracy, provider, mock flag and fix time are evidence only, **not** geofence clearance, productivity or per-diem credit. Note and checkout can queue after check-in without network. Each check-in gets a fresh lowercase UUID request ID and client visit UUID; dependent operations reference the check-in request UUID in `dependsOn` and store a local `@checkin:<UUID>` template reference. **This template is never sent**: after a durable check-in ack, the send path resolves it to the actual server `visitId`. The v1 wire requires a server ID for dependent payloads, so an offline queued dependent cannot itself already be a complete valid v1 wire operation; its immutable intent/template and ID are durable, and its outgoing bytes are deterministic after resolution. Check-in and outbox insert together in Room; ack insert and done transition share a transaction. No status is accepted from a transport timeout or unknown response.

`VisitSync` obtains a fresh challenge for each signed request/401 retry, signs the exact UTF-8 body, pulls with limit 50 and persists revision/tombstone changes with the next cursor transactionally, including empty filtered pages. The scoped delta table does not overwrite snapshot rows or local pending intents. Push is single-flight on the engine instance, sends at most 20 ordered operations and freezes rejected/conflicting/unknown results. Uncertain transport outcomes retain original IDs/bytes for replay; bounded jittered retry is foreground-only. On 409 the outbox is held through verified bootstrap; revalidated planned/outlet/day work can resume, changed work moves to review. A changed scope leaves the old partition held for administrator review. Unresolved 401 holds work conservatively; offline revocation cannot be detected. WorkManager is **not** implemented here. Late check-ins up to seven days old remain eligible after cursor recovery when serviceDate matches the Manila deviceTime date and their cached assignment remains valid. Production/pilot is not authorized.

**Wire differences:** frozen `error-*.json` fixtures nest error details while the runtime emits flat fields; both decode. `push-request.json`'s second operation references a literal server visit ID despite the same request carrying a check-in; the working fake device sends check-in first, takes its ack entity ID, then sends note/checkout. `push-response.json` is an independent fixture whose second request ID and kind do not correspond to the second `push-request.json` operation. The native engine follows the actual server/fake-device sequence, not an invented visit ID. The TypeScript fake signs handset `Date.now()`; Android derives proof time from challenge expiry. Unknown response statuses freeze for review even though strict full-envelope schema validation would reject them.

**Lead's authorized DEV run:** configure ignored `local.properties` with the matching DEV site/functions origins; install only `com.sunpride.field.dev` on the chosen test device. Have an admin register/bind a scoped seller phone as described above; sign in with the approved account, open Today and Sync now while online, and confirm a Manila-today planned visit or a permitted cached unplanned outlet. Open **DEV visit** from a row, allow precise location on the device (never grant via adb on the real phone), then disconnect network _after_ bootstrap. Start, optionally Add note, select outcome (and nonproductive reason), and End call; observe Queued and stale. Force-stop/relaunch while offline and check the queued count persists. Reconnect, Sync now; confirm Accepted or Needs review, cursor progress and exactly one server visit via authorized readback. For a replay/conflict proof, use a separately authorized signed client and the same request ID/body first, then changed payload with the same UUID; never mutate the phone's immutable row. If check-in is rejected, dependent work stays in review. Sign out and remove `com.sunpride.field.dev` after evidence collection. Do not put credentials, bearer, coordinate payloads or raw database contents in reports.

## Sync visibility, background work and diagnostics (issues #60, #62, #63)

Today has a compact sync label and a details/review sheet. Its queued, sending, needs-review and held counts, last successful sync, cache expiry and lease expiry come from encrypted Room, not a network success message or SharedPreferences timestamp. ConnectivityManager observes offline state without toggling connectivity. Rejection codes are mapped to fixed plain-language reasons; the raw server message, request body and identifiers are not shown. “All synced” is impossible while unresolved work exists or cache/lease is stale. Manual Sync now and the worker enter the same per-partition `VisitSync` mutex; a concurrent second flight is a no-op and keeps queued state visible. Sending is a durable transient marker reset to pending on interruption; ack + done remain transactional.

A visit enqueue schedules `SyncWork` **after** the Room transaction commits. App startup with eligible pending work and foreground sync with remaining work also schedule it. WorkManager's unique `field-visit-sync` chain uses `APPEND_OR_REPLACE` so a commit during an active worker cannot lose its wake-up, a `CONNECTED` constraint and exponential backoff. Work is best effort under Doze/battery policy; no exact delivery window, alarm, foreground service or background location is requested. Held partitions do not push. Day-close/expired offline access blocks new enqueue, not delivery of already-durable work; late work is still pushed and held for supervisor review server-side. To inspect or force a scheduled job **on the emulator only**, use `adb -s emulator-5554 shell dumpsys jobscheduler com.sunpride.field.dev` and `adb -s emulator-5554 shell cmd jobscheduler run -f com.sunpride.field.dev <job-id>` after extracting the WorkManager job ID. No DEV sync is part of automated tests.

Support info is copyable and includes only app/build, Android version, an opaque random per-install handle, local counts and a fixed outcome code. It contains no key fingerprint, server/device identity or raw visit payload. `Redactor` masks known secret/contact/location forms, while `SafeLog` accepts only fixed event codes and emits Logcat events only in debug builds. A private noBackup breadcrumb ring holds the last 50 allowlisted redacted events; the uncaught-exception handler records `crash` and delegates to the prior handler without serializing a Throwable. No third-party telemetry SDK is used.

## Daily route (issue #51, AND-010)

Today links to a **Route** page that lists today's planned outlets from the encrypted cache, so it works with no signal. Stops are numbered in MCP sequence (download order when sequence is absent), the same order the Start/End rules enforce. Each stop shows its state (Next, Later, In progress, Done, Needs review; a stop in review still holds back later stops), straight-line distance from a one-shot foreground fix, and two actions: **Navigate** hands a `geo:` URI to the user's maps app (verified pin first, address search as fallback, disabled when neither exists; "No maps app on this phone" if nothing can open it) and **Customer** shows outlet/customer codes, address and planned intents, with **Open visit** in builds where visit recording is enabled. Opening the page never prompts for location: a fix is taken only when already permitted, otherwise **Show distance** asks. The fix is not stored or sent. Bootstrap v1 outlets carry additive optional `code`, `customerId`, `address` and `latitude`/`longitude` (a single current verified pin; both or neither); older servers omit them and the page still lists stops without distance. ## Customer search and outlet detail (issue #52, AND-011)

Today links to **Customers**: an offline search over the outlets in the signed-in person's active snapshot (the server only sends outlets on their own plan, so search cannot reveal anything outside their scope). Every typed word must match the outlet name, outlet/customer code, address, Annex C account or buyer name, or route code; matching ignores case and accents ("sto nino" finds "Sto. Niño"). Exact codes rank first, then name prefixes, then today's route order. Opening an outlet shows: the summary (codes, address, pin state, Annex C account header: buyer, contact, account/receiving in charge, distributor and schedule, FOC), the route (the person's route code, today's stop number and state), planned visits across the downloaded days, tasks (today's planned activities at this outlet plus the person's own day tasks, which v1 does not tie to an outlet), and recent history recorded on this phone (start, notes, call sheet, end with outcome, and whether each was sent). Office history from other phones is not on the v1 wire and is labelled as such. Actions: **Navigate** (same `geo:` rule as the route), **Call** (hands a `tel:` URI to the dialer; disabled when the contact is not a phone number) and, where visit recording is enabled, **Open/Continue visit** or **Unplanned visit**. Tests: `CustomerDirectoryTest` (JVM), `CustomerScreensTest`, a store scope case in `EncryptedFieldStoreTest` and a Today → Customers → Outlet → back case in `FieldAppTest` (emulator).

## Offline order drafts (SP-0061, AND-014)

During an open call (after **Start**, before **End call**) the visit screen has an **Order** section: **New order** opens an editor that searches the account's product setup offline (code, name or barcode; case- and accent-insensitive; exact code/barcode first) and takes a whole-number quantity (1–99,999) per product in the setup UOM. **Save draft** writes the draft to the encrypted Room table `order_drafts` (schema v7, explicit non-destructive `MIGRATION_6_7` layered on the v6 photo table), partitioned by subject/device/scope like every other row; saved drafts reopen from the visit for editing or **Discard**. Drafts are local only until reviewed and sent (SP-0060, below).

- **Authorized catalog:** the account's server-owned Annex C call-sheet lines from the scoped bootstrap. The nationwide product master is never offered, and `productCatalog` stays empty (the decoder still rejects a non-empty one).
- **Price/UOM rules:** v1 bootstrap sends `priceAvailability: "unavailable"` (no governed price list yet, ADR-008), so a draft records quantities only. It has no unit price, amount or total, and it stores `priceAvailability: "unavailable"`. The account's free-text pricing note appears as a reference only. A quantity is always in the line's setup UOM. No UOM conversion is cached on the phone.
- **Association:** each draft is built from the stored check-in and the cached snapshot, never from user input. It records the client visit and check-in request IDs, planned visit, outlet, service date, customer ID and code, route, and territory. Territory comes from the additive optional bootstrap `outlets[].territoryId/territoryCode`, taken from the signed planned-visit snapshot; older servers omit it and the draft stores null. `OrderDraftRules.validate` re-checks all of this inside the Room transaction: the call must still be open, products must be in the current setup with the same code, name and UOM, the catalog revision must match, and the identity cannot change. A held partition freezes both save and discard. If the office later removes a product, the editor flags that line as stale and drops it on the next save.

Tests: `OrderDraftTest` (JVM: catalog search, quantity rules, association, forged/stale/held refusals, controller save/update/discard), territory cases in `BootstrapTest`, plus emulator `EncryptedFieldStoreTest` (SQLCipher persistence, scope isolation, frozen after End/hold), `StoreMigrationTest` (v6 → v7 and the full v1 → v7 chain) and `DiagnosticVisitTest.captureOrderDraftOfflineFromTheAccountCatalog` (UI end to end with a screenshot).

## Order review and submission (SP-0060, AND-015)

A saved draft whose screen matches what was saved shows **Review order** instead of **Save draft**. The review lists each line (name, code, quantity and unit), the total (number of products and units per unit of measure, e.g. "2 products · 24 PC · 12 CAN"; there is no amount while the server says prices are unavailable, so it reads "Amount: priced by the office"), and the rules the phone can check offline: call still open, products still set up for the account (same revision, code, name, unit), whole quantities 1–99,999, today's offline access still valid, and not already sent. **Send order** is enabled only when every check passes.

- **Submission** queues the visit's v1 `visit.activity` with `order_intent` `{clientOrderId: draftId, lines: [{productId, uom, quantity}]}` (additive optional `lines`, no prices) behind the call's latest request. `FieldStore.submitOrderDraft` enqueues it and marks the draft sent (`submittedRequestId`, `submittedAt` inside the draft JSON; no schema change, older rows decode as unsent) in **one** Room transaction. `OrderQueueRules` re-checks inside enqueue that the request matches an unsent local draft of the same call exactly, so a forged, changed or second request never reaches the outbox. A sent draft cannot be edited, discarded or sent again.
- **Idempotency:** one immutable request ID per order (replayed unchanged after an uncertain send), and the server refuses a second `order_intent` with the same `clientOrderId` on the visit (`conflict`). The local `@checkin:` reference is replaced by the server visit ID only after the check-in ack, like every dependent visit operation.
- **Status** comes from the outbox: Draft · not sent, Waiting to send, Sending, Received by office (acked), Not accepted · needs review (rejected/conflict), Not sent · call ended (unsent draft after End). The visit screen lists orders with their status and warns before End when a draft is unsent; a sent order reopens read-only.
- An office activity rule that requires `order_intent` is now capturable when the account has products, and a queued order satisfies it.

Server: `convex/orders/field_order.ts` checks the account setup exists, each product is usable and in its current unit, quantities are whole 1–99,999, and one submission per phone order; lines are stored on the visit's `order_intent` activity. ## Supervisor team view (issue #61, AND-020)

A supervisor signs in on the same field app (supervisors are the `manager` app role in their assigned unit, ADR-009). When the active snapshot's employee role is one the server lets read a team (`manager`, `super_admin`, `admin`, `analyst`, `viewer`: `people.read` and `visit.read`), Today shows a **Team** link. The link is only a hint: the server decides every read, and field `sales` is refused.

The **Team** page calls the Convex query `supervision/mobile:team {serviceDate, directOnly}` with the Convex JWT (same path as `devices:mine`, not the signed device HTTP API). The server resolves scope exactly like the web supervision views (`supervision/access.ts`: current org subtree, current employee assignment) and returns one compact read: each person's day (planned, planned done, productive, nonproductive, unplanned, in a call, out of MCP order, open exceptions, late sync) and up to 50 of the day's exceptions, open first (outside radius / unreliable location, out of MCP order, unplanned, nonproductive, rescheduled, cancelled, not visited). It defaults to **direct reports** (`employeeAssignments.supervisorId` or the legacy `supervisorSubject`); **Whole area** asks for the caller's full subtree. No raw device coordinates, actor tokens or audit history are sent; geofence decisions stay on the web ("Needs review on the web").

Caching: each successful answer is saved in the signed-in partition of the encrypted Room store, in the existing `deltas` table under the reserved local entity `local.team` keyed `<Manila date>|direct|all` (no schema migration; server deltas only write `visit`/`activity`). Only today's copies are kept, nothing is saved for a held or never-bootstrapped partition, and another account/device/scope never sees it. Offline, the page shows today's saved copy for the same filter, labelled with the time it was saved; a server refusal or expired session never shows saved data. Every visit to the page and **Update** asks the server again.

Tests: `TeamSummaryTest` (JVM: wire decoding, refusal vs offline, wrong day/filter, wording), a controller case in `FieldControllerTest`, `TeamScreenTest` and a Today → Team → back case in `FieldAppTest` (emulator), and the scoped cache in `EncryptedFieldStoreTest`. Backend: `supervision/supervision.test.ts` "mobile supervisor summary (AND-020)". Not done here: a live DEV proof with a real supervisor phone (needs a registered device for a manager account), and an iOS equivalent.
