Big picture

SAP stays the master
Prices, credit, stock value and accounting come from SAP. Sunpride keeps a copy and sends work back.
Phones work offline
They save on the phone and send when there's signal. Phone chat refreshes every few seconds; only the web updates instantly.
Scheduled tasks live inside the server
Sending to SAP, nightly and weekly reports, claim and alert emails. Reminders aren't built.not built
SAP is a test copy today
The connection to the real SAP is prepared but not connected or tested.not built
Email is in test mode
Emails are recorded but not sent until a mail service is switched on.partial

Roles
Super admin, admin, operations, manager, approver, sales, analyst, viewer. The server rechecks the role and area on every action.
Field and van sellers share a role
Both are "sales". The difference is the phone they're given and, for van sellers, an assigned van. Admins register every phone.
Managers use web and phone
The Field app shows them their team's day and work-with visits.
Messages and Issues are for everyone
Anyone can chat and file an issue. Admin, operations, manager and approver work the issue list.
Distributors
They have their own partner portal on the web and a partner mode in the Field app. Not drawn here.

Planning
Approval must come from someone other than the person who made the plan. Once approved, visits appear on the phone by themselves.
Location
Fake, weak or old locations are refused. Calling outside the store's radius needs a supervisor's OK.
Call sheet
The product and quantity form for each store. Which in-store steps are required depends on the channel.
Suggested order
The screen exists inside the call sheet but shows no suggestions until the analytics feed is connected.partial
Census and collections are separate
Census captures a new store (GPS and photo). Collections run from a Collector agenda, not inside a visit.
DAR / ROAR
Filed by the supervisor or route seller on the web by 10 pm. A productive call is a planned visit closed with a qualifying activity.
04

Order to SAP

A field order goes to SAP only after a different person approves it. Saving an order doesn't move stock.

sequenceDiagram
  autonumber
  participant P as Field app
  participant S as Sunpride server
  participant O as Office approver
  participant Q as SAP queue
  participant SAP as SAP (test copy)
  P->>P: Save order on the phone
  P->>S: Send when online, quantities only
  S->>S: Check seller, store, products
  S->>S: Set prices, ask SAP about credit (advice)
  S->>S: Save order, approval request, audit together
  S-->>P: Received by office
  O->>S: Approve (not your own)
  S->>SAP: Reserve credit, waits if SAP unknown
  S->>Q: Add to SAP queue
  Q->>SAP: Send order
  SAP-->>Q: Document number
  Q->>S: Store SAP number, order stays Approved
  Note over Q,SAP: If SAP is down: 5 retries,
then an operator retries
Prices come from the server
The phone sends products and quantities. The server prices them from its copy of SAP price lists.
Credit is checked twice
As advice when the order arrives, then reserved in SAP at approval.
Problems go to the office
If an order can't be created it appears on an office review list, not on the phone.partial
Not built yet
Moving to "Posted" automatically, SAP status on the phone, and the real SAP connection.not built

Van stock & cash

Stock only moves through one ledger. A day closes only when warehouse, office and a second supervisor all agree.

    TOL -- "yes" --> SIGN["Second supervisor

    VAR --> SIGN
    WH --> SIGN
    CASH --> SIGN

  end
  TRK --> CNT
  DMG --> CNT
  OK -. "settlement, invoices, payments" .-> Q["SAP queue"]

  class TRK,SIGN core
Loading
The office plans the load; the phone confirms what really went on. Differences need a second person.
Selling
Checked against the official price and credit. A numbered Sales Invoice prints at once. Sample invoices say "not tax documents".
Voids
Need an office code. Stock is put back and SAP gets a credit memo. Nothing is deleted.
Returns
Must link to the original receipt. Returns without a receipt, or needing approval, aren't supported yet.partial
Proof
Fully coded on the server and phone, not yet proven on a real handset with the live server.partial
06

Offline & sync

Each phone keeps a locked local database and an outbox. Sync sends the outbox and pulls what changed.

flowchart LR
  subgraph PHONE["Phone"]
    direction TB
    UI["App screens"] --> LDB[("Encrypted local data")]
    UI --> OUT["Outbox
work waiting to send"]
  end
  OUT -- "send, signed by this phone" --> SYN["Server sync"]
  SYN -- "changes for my role and area" --> LDB
  SYN --> CHK{"Each item
allowed?"}
  CHK -- "yes" --> ACC["Accepted
saved once only"]
  CHK -- "no" --> REV["Needs review
on the phone"]
  LOSS["Signed out, phone removed,
area changed"] --> HELD["Held
nothing is sent"]
  SYN -. "nudge" .-> WEB["Web pages refresh"]

  class SYN,LDB core
  class HELD partial
Sending twice is safe
The same work is never saved twice.
One refusal doesn't block the rest
A refused item shows "Needs review"; everything else goes through.
Lost access
Sync freezes and downloaded data is cleared. Unsent work stays on the phone for review.partial
Tied to the device
Every send is signed by the phone's own key, so a stolen password alone isn't enough.

How changes ship

Feedback goes into Issues. Automated builders fix it, a landing check publishes it, and the reporter retests.

flowchart LR
  R["Issue filed"] --> BL["Backlog"]
  BL -- "every 10 min" --> IP["In progress
automated builders"]
  NF["Needs fix"] -- "first in line" --> IP
  IP -- "automated checks" --> QA["In QA
waiting to go live"]
  QA -- "every 20 min" --> LIVE["Web + server
go live"]
  QA -- "problem" --> NF
  LIVE --> RT["Ready for retest"]
  RT --> Q{"Reporter
comment"}
  Q -- "works" --> DONE["Done"]
  Q -- "still broken" --> NF
  IP -. "question" .-> AW["Awaiting client
response"]
  AW -. "moved back by hand" .-> NF
  LIVE -. "phone code changed" .-> APK["New phone app
to Drive"]

  class IP,LIVE core
  class AW,APK partial
Seven stages
Backlog, In progress, In QA, Needs fix, Awaiting client response, Ready for retest, Done.
Checks are automated
Builds pass type checks, tests and lint. Nobody tests on real phones during the build.
Web goes live in about 20 minutes
At the next landing check, not instantly.
Phone apps every 2 hours
Only when phone code changed. Recent uploads to Drive have failed and need a fix.partial
Answers to questions
A client reply isn't picked up automatically yet; someone moves the issue back.not built
To update, edit apps/web/public/flow/index.html. Instructions are at the top of the file.
