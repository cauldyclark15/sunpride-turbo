# ADR-011: Configurable organization hierarchy and historical scope

Status: accepted (2026-09-25, JC lead) — provisional items marked inline

## Context

ADR-005 already makes `orgUnitTypes` the configurable levels and `orgUnits` the nodes. The seeded National → Region → Area → Territory path is a starting configuration, not a fixed taxonomy. The blueprint §3 explicitly warns against hard-coded hierarchy names; §42 requires subtree rather than nationwide visibility. The client memo calls for standards across territories and territory expansion (memo §§1, IV), but does not define the canonical reporting tree. A present-day `parentId` alone cannot reconstruct yesterday's chain after a reorganization (`packages/backend/convex/schema.ts:1186-1215`).

## Decision

- Keep **one Sunpride organization** (`organizationId = "sunpride"`), per ADR-005. `orgUnitTypes` is an ordered, organization-scoped configuration (`code`, `label`, `level`, `active`); `orgUnits` references it through `typeCode`. National, Region, Area, Territory are seeded _labels_, never required literals or columns. A tree can add or rename a level without changing endpoint permissions. Type codes and unit IDs are stable; change a label, not the identity. Changing level order is a governed migration with validation, not an unreviewed edit.
- Exactly one active national root is accepted; only the configured root has no parent. Every other current unit has exactly one active parent in the same organization, of a strictly lower configured level; intermediate levels may be skipped when configured, but cycles and orphaned units are refused. The parent interval must cover the child's effective interval. No sibling requirement is implied. **Provisional — pending client confirmation:** whether Sunpride wants a single tree across channels or separate channel branches below the root; until confirmed, channel is an attribute (ADR-009), not a forced hierarchy level. The blueprint §3's example channel layer is illustrative, not binding.
- Interpret dates as half-open `[effectiveFrom, effectiveTo)` intervals in the organization's business timezone for planning, stored as unambiguous timestamps. A unit's immutable ID and code survive a move. Persist **effective-dated parent edges** (unit, parent, from, to, actor/reason), and effective-dated employee-unit/supervisor assignments; no overlapping active parent or primary assignment intervals. `orgUnits.parentId` and `profiles.orgUnitId` remain current projections for existing code, not historical truth. Close the prior edge/assignment and append the next; never rewrite visits, orders, approved MCP versions, or old reports. This extends ADR-005's existing `orgUnits.effectiveFrom/effectiveTo` and assignment rule, rather than replacing its schema.
- Reorganizations take effect prospectively by default. Approval checks use the **current** subtree and the actor's active assignment; a historical report resolves edges/assignments as of its recorded business time and names that time. A future transfer does not retroactively grant access to old records; access to historical records follows current authorized subtree plus record-level ownership or an explicitly authorized historical reporting view, not yesterday's unrestricted subtree. **Provisional — pending client confirmation:** whether historical reports follow original or current managerial attribution; default to original for performance/audit, current for operational worklists.
- A territory may be an `orgUnits` node of a configured type; a future geographic territory/polygon is a separate linked coverage entity (`CVX-005`), not the permission root by itself (glossary, “Territory”). Routes, teams and outlets reference stable units/territories by ID with effective-dated assignments; they do not encode a fixed Region/Area/Territory path (blueprint §§3–5). The memo's planned MCP calls and per-diem evidence must retain the approved plan's assignment at that time (memo §II); no retroactive entitlement change from a move.

## Consequences

- Add historical edge and assignment records plus overlap/cycle/coverage validators; keep existing `orgUnits` and `orgUnitTypes` indexes and current `parentId` projection (`CVX-004`, `CVX-005`, `CVX-023`). Migrating existing rows requires an initial edge at their existing effective start. `profiles` is still the employee record until ADR-005's HR split; `assignPersona` currently patches one unit without closing historical intervals (`domains/profiles.ts:434-482`).
- `collectScopeUnitIds` today walks active `parentId` and has a 500-unit cap (`lib/scope.ts:19-78`); replace or augment it with effective-time-aware bounded traversal for historical queries and fail closed on invalid/oversized trees. All scoped queries must filter server-side. Current `requireCapability` without a target checks only the role, not scope (`lib/capabilities.ts:98-125`).
