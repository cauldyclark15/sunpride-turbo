# ADR-022: Offline authority and conflict matrix (SFD-008)

Status: accepted (2026-10-07, Turbo default per jc) — **provisional until Sunpride signs off**. Sunpride was not asked first (jc, 2026-10-07: "do not wait for Sunpride … server wins for master data and approvals, phone wins for its own visit facts, conflicts held for review"). Sunpride may change any row; the change is one edit to the data table below plus this record.

## Context

ADR-002 and ADR-019 set the offline rules in prose; ADR-020 covers device trust and ADR-021 the bootstrap/pull/push transport. SFD-008 asks for one approved matrix: for each synchronized entity, whether it is server-authoritative read-only data, a device-editable draft, an append-only event or a server workflow state, and how idempotency, stale revisions, ordering, retries, conflict responses and user remediation work — with the rule that **device clocks never decide business order**.

## Decision

The matrix is code, not only prose: [`packages/domain-contracts/src/offline-authority.ts`](../../packages/domain-contracts/src/offline-authority.ts) exports `OFFLINE_AUTHORITY_MATRIX` (one row per entity), `OFFLINE_OUTCOMES` (one row per outcome code) and `OFFLINE_POLICY` (retry and limit defaults). `packages/domain-contracts/test/offline-authority.test.ts` fails when the mobile v1 or van v1 schema gains a bootstrap section, push kind or outcome code, or the backend writes a pull entity or returns a business code, that the matrix does not classify. `OFFLINE_POLICY.source` is `"turbo-default"`; flip it to `"sunpride-approved"` (and update this status line) when the client signs off.

### Four authority classes

| Class             | Who writes                          | Device may                              | Stale copy                                                          | Examples                                                                                                    |
| ----------------- | ----------------------------------- | --------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Server read-only  | Server                              | Cache and display (labelled "as of")    | Replaced by a whole bootstrap generation or a higher pull revision  | Outlets, catalog, customers, stock availability, activity rules, account summaries                          |
| Server workflow   | Server                              | Request a transition; never set a state | Same, or a forced rebootstrap                                       | MCP plan status, planned stops, visit certification/productivity, trip and load status, approvals, postings |
| Append-only event | Device creates, server accepts once | Create; never edit after queueing       | The queued bytes never change; same ID + different bytes = conflict | Check-in, activity (notes, checks, call sheet, order intent), check-out, photo evidence, truck damage       |
| Device draft      | Device only                         | Edit freely                             | Never leaves the phone until submitted                              | Open call's unsaved answers, order draft before Send, load/end-of-day count in progress                     |

Summary rule: **the server wins for master data, plans, approvals, postings and every workflow state; the phone wins on what it observed (its own visit facts, times, places, photos) and those facts are never rewritten; anything that cannot be accepted as-is is held for review — never merged or deleted automatically.**

### Ordering and time

- Business order is the server's: `mobileChanges.sequence` for the pull feed, the server's transaction order for workflow and postings, and the ack `serverTime` as the official time. The **device clock is evidence only** (when the rep says it happened, call duration) and is range-checked: more than 24 hours ahead of server time, or older than the 7-day late window, is refused without writing anything.
- The phone sends its outbox oldest-first, at most 20 operations per push, one in-flight sync per device scope. The server enforces `dependsOn` (activity/check-out need an acknowledged check-in), one open call at a time and approved-plan stop order; it never reorders by device time. Proven by `convex/mobile/push.test.ts` "orders by server arrival, never by device clock…" and the chaos suite.

### Outcomes, retries and remediation

| Outcome                                                                                                                                                | Phone does                                                                                                       | Same bytes resent?                                       | Rep sees                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------- |
| accepted                                                                                                                                               | Store ack, mark done                                                                                             | —                                                        | "Synced at <server time>"                                   |
| temporarily_unavailable / no answer                                                                                                                    | Keep queued, retry with jittered backoff 5 s → 15 min; "Needs attention" after 5 failures, safe retries continue | Automatic (replay returns the stored ack)                | "Saved on device • N pending"                               |
| rebootstrap_required / invalid_cursor / scope_changed                                                                                                  | Hold, rebootstrap, resume; old-scope work stays held for review                                                  | Automatic (scope change: only after verified same scope) | "Refreshing today's plan…"                                  |
| dependency_missing                                                                                                                                     | Wait for the earlier step's ack                                                                                  | Automatic                                                | "Waiting for the check-in to sync first."                   |
| conflict                                                                                                                                               | Freeze row for review; later independent rows continue                                                           | Never                                                    | "Needs review: this was already recorded differently."      |
| invalid_request (incl. reasons call_open, mcp_order, wrong_date), invalid_plan, out_of_scope, evidence_pending_review; van wrong_date, load_not_posted | Freeze row for review                                                                                            | After the cause is fixed (or never, per row)             | Plain reason per code                                       |
| unsupported_operation                                                                                                                                  | Freeze row; kept on phone                                                                                        | After the feature ships                                  | "Saved on this phone; this feature is not switched on yet." |
| unauthorized / device_revoked                                                                                                                          | Hold whole outbox; recheck registration before treating as removed                                               | After sign-in (never after confirmed revocation)         | "Sign in again…" / "This phone was removed…"                |
| version_unsupported                                                                                                                                    | Hold until updated; queue survives upgrade                                                                       | After update                                             | "Update the app to keep syncing."                           |

Per-code text and owner live in `OFFLINE_OUTCOMES`. Conflicts, scope problems and evidence questions are never auto-resolved (`OFFLINE_POLICY.neverAutoResolve`); the supervisor resolves them on the web and any re-recording is a new record with a new ID.

## Consequences

- New sync entities, operation kinds or codes cannot ship unclassified: the contract test fails first.
- Native apps (`apps/field-android`, `apps/field-ios`, `apps/van-sales-android`) already behave this way (409 → hold + rebootstrap; 401 → hold; rejected/conflict → frozen review row; other failures → backoff); this record states it as policy rather than changing them.

## Open items

- **Sunpride to confirm** (no answer needed to run): who resolves held conflicts (default: the rep's direct supervisor), the 7-day late window, the 24-hour device clock tolerance, the retry/attention defaults, and whether a collection recorded offline may be printed before acceptance.
- The backend returns per-operation code `invalid_plan` (planned stop replaced/changed), which the frozen v1 result-code enum does not list; strict decoders must keep it as an unknown raw code. Fix in a v1-additive `reason` or v2, not by editing the frozen enum.
- `scope_changed`, `device_revoked`, `evidence_pending_review` are reserved in the v1 enums but not emitted today (the server answers 401 / rebootstrap instead); their rows define the behaviour when they are.
