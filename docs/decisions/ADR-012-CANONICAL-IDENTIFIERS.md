# ADR-012: Canonical identifiers independent of SAP

Status: accepted (2026-09-25, JC lead) — provisional items marked inline

## Context

ADR-002 gives offline orders a stable `clientRequestId`; ADR-006 makes `products.code` immutable and keeps SAP/supplier identifiers separately. ADR-005 owns organizational IDs; ADR-007 owns inventory location identity. The blueprint §§5, 33, 43–45 distinguishes outlet operations from SAP customer accounting, mandates retry-safe outbox keys, and stores the ERP document number only after asynchronous integration. An SFA record must exist before any SAP mapping exists.

## Decision

Every entity has one immutable, server-owned Convex `_id` as its internal relational key. Human codes are organization-scoped, unique within entity type, normalized at entry, never reused after retirement; labels and names are mutable display text. External identifiers are **optional, namespaced by source system and entity type**, unique where the source promises uniqueness, and never become primary keys. An external ID may be remapped only through an audited, effective-dated mapping; conflicting imports enter review, not silent overwrite. For legacy `externalId`/`externalCode`, the adapter treats the value as a source-specific mapping, not proof that it is SAP.

- **Offline creation:** iOS, Android field and van clients generate a UUIDv7 (or equivalent collision-resistant 128-bit random ID when a monotonic clock cannot be trusted) once per locally created visit/order/transaction. Persist it atomically with the outbox record; retry with that _same_ `clientRequestId`/idempotency key and identical payload, never generate a replacement on retry. Namespace uniqueness by organization and entity/command kind, and reject same key with a different payload (ADR-002; blueprint §§32–33). The backend assigns `_id` and returns a durable client-ID → server-ID acknowledgement. Existing order `clientRequestId` is a UUID contract, not a second mutable human order number.
- **No SAP identifier is required to operate SFA.** Locally sourced master rows, routes, visits, orders, MCP and operational stock function with Turbo IDs/codes; integration queues unresolved mappings for review before ERP posting, never blocks recording a valid offline business event. SAP may reject a financial post; preserve the Turbo record and surface reconciliation rather than forging an ERP ID (ADR-003/006/007; blueprint §§43–45).

## Consequences

- Add source-qualified external-ID mapping/history and uniqueness checks; preserve existing `externalId`, `externalCode`, `customerCode`, `productCode`, `orderNumber` and `clientRequestId` during migration (`schema.ts:74-115,154-170,255-286,1045-1095,1186-1215`). Do not silently treat `customers.territory` text or `salesAssignments.territory` text as canonical foreign keys.
- Create stable team/territory/route/outlet tables and historical relationships when those domains land. Add client IDs to offline visits and other field/POS records; today's `visits` has no such field, while orders already have `clientRequestId`. Resolve duplicate UUIDs and cross-device retries with a unique lookup and payload hash.
