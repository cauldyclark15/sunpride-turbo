# Mobile device authentication v1 — slice B

**Status:** device lifecycle and internal proof primitive implemented; `/mobile/v1/*` HTTP routes and real DEV bearer smoke test are **not** implemented/performed in slice B. Do not claim native HTTP auth is proven until slice F exercises it on DEV. No password, session token, JWT, private key, or proof may be logged.

## Online enrollment and request flow

1. An invited, active employee signs in online through Better Auth at `CONVEX_SITE_URL/api/auth/sign-in/email` with the normal credentials and an allowed `Origin` (`WEB_SITE_URL` or `PWA_SITE_URL` in `convex/auth.ts`). Native integration must validate the origin/trusted-client policy with security before production; do not spoof an origin as a permanent native policy. Better Auth's bundled bearer plugin returns the **session token** in `set-auth-token` on email sign-in; store it only in the platform secure store. This session token is **not** the Convex JWT.
2. Request `GET CONVEX_SITE_URL/api/auth/convex/token` with `Authorization: Bearer <Better Auth session token>` (or the valid Better Auth session cookie). Read the JSON `token` field; the bundled `convex()` plugin issues a Convex-audience JWT, default expiry 15 minutes. `apps/web/src/lib/auth-client.ts` uses `convexClient()`; `@convex-dev/better-auth/src/react/index.tsx` calls `authClient.convex.token`, and its plugin registers `/convex/token`. `convex/auth.config.ts` uses `getAuthConfigProvider()` for that JWT. Renew via the Better Auth session as needed; never substitute the session token itself as the Convex bearer.
3. A scoped admin registers an already-generated non-exportable device public key with `devices.register({inventoryTag,allowedApp,platform,model,osVersion,appVersion,profileId,publicKey})`. Key is base64 DER SPKI **ECDSA P-256**; private key stays on the phone. Only `IOS`/`ANDROID` matching `iOS`/`Android` are accepted, not `VAN_ANDROID`. One active device per employee and tag; revoke the old one after reconciling unsent outbox before replacement. Enrollment does not grant an anonymous client access.
4. Employee calls `devices.challenge({deviceId})` with the Convex JWT; server creates a one-time UUID nonce valid for 60 seconds. For first bind, sign UTF-8 `BIND|deviceId|credentialId|nonce|timestamp` with ECDSA SHA-256 (WebCrypto signature format, 64-byte IEEE P1363 `r||s`, base64), then call `devices.bind({deviceId,credentialId,attestation:{format,keyId?},nonce,timestamp,proof})`. `timestamp` is integer UTC epoch milliseconds, at most ±60 seconds from server. The attestation metadata is **unverified**, not a claim of hardware integrity; actual attestation verification requires a separate security review. Bound subject is the full `issuer|subject` from Convex identity.
5. For each HTTP request, obtain a **fresh** challenge with the JWT, hash the _exact raw request body bytes_ with SHA-256 to lowercase hexadecimal, and sign UTF-8 `POST|/mobile/v1/<bootstrap|pull|push>|bodyDigest|nonce|timestamp`. Send base64 signature, nonce, timestamp, app identifier, device ID and `Authorization: Bearer <Convex JWT>` in the route protocol defined by F. F must compare its own raw-body SHA-256 digest to the signed digest before invoking `internal.mobile.device_auth.authorize`; never take a caller-supplied digest as verified. The internal mutation checks current bearer identity, active bound device, persisted app, current effective assignment/role/unit, signature, nonce expiry/reuse and skew **atomically**; it burns the nonce only on success and returns `{deviceId,profileId,subject,orgUnitId,role,scopeFingerprint}`. Scope fingerprint hashes profile, full subject, assignment row, unit, role, device, app and credential; assignment renewal/transfer invalidates the previous cursor. F must authorize before _every_ bootstrap/pull/push and before replay lookup.

Convex documents HTTP action `ctx.auth.getUserIdentity()` when called with a JWT in the `Authorization` header. **Unverified integration detail:** whether `ctx.runMutation(internal.mobile.device_auth.authorize, ...)` retains that authenticated identity must be demonstrated on DEV, not inferred from `convex-test`; if it does not, stop and redesign the trust boundary without accepting caller-supplied `identity` or `--identity`. The SAP connector HMAC and a bare `deviceId` are never mobile authorization.

## Exact DEV smoke-test checklist (after F routes exist)

- Have an invited active DEV account and an admin in the employee's stored unit; confirm `CONVEX_SITE_URL` ends in `.convex.site`. Sign in through the Better Auth endpoint above from a trusted origin; hold the session token privately, exchange it through `/api/auth/convex/token`, and inspect only JWT metadata (`iss` = site URL, `aud` = `convex`, expiration in future), never print token contents. Sign-in with an unapproved native Origin may fail `MISSING_OR_NULL_ORIGIN`: resolve trusted-client policy, not an auth bypass.
- With the Convex JWT as bearer, call the existing `domains.profiles.current` over an authenticated Convex client and verify an active profile with the **full** subject. As an admin register a disposable key/device; as the employee issue challenge and bind using real key possession. Do not use CLI `--identity` as proof.
- Request a new challenge, sign a real `/mobile/v1/bootstrap` POST byte body as above, send JWT + proof headers per F, and confirm HTTP action `ctx.auth.getUserIdentity()` and internal authorizer resolve the same full subject. Retry exact nonce: denied. Send a valid JWT with a wrong signature: denied. Use another user's JWT: denied. Revoke through admin API, send a new attempt: denied. Read back exact challenge/device rows and redacted audit, not only HTTP status. No live sign-in was performed in slice B.

## Employee device lookup after admin registration

After online sign-in and Convex JWT exchange, the phone generates its P-256 key pair locally and shows only its base64 DER SPKI public key to the admin. The admin registers that exact key for the employee profile with `mobile/devices:register` (DEV CLI: `bun run packages/backend/scripts/register_device.ts --admin-jwt-file PATH --profile-id ID --app IOS|ANDROID --public-key-file PATH`; `CONVEX_URL` required). The employee then polls the authenticated public **query** `mobile/devices:mine({publicKey,app:"IOS"|"ANDROID"})` over `${CONVEX_URL}/api/query` with their own Convex JWT until it returns `{deviceId,status,bound,allowedApp}`. `null` means no matching device for this employee/key/app (also unauthenticated); do not infer whether a different employee owns the key. Match SPKI base64 exactly. A `revoked` status means stop and ask an admin; do not challenge. `bound` is true only when both `boundSubject` and `credentialId` are stored after successful bind; an active unbound row proceeds to `mobile/devices:challenge({deviceId})`, then signs and calls `mobile/devices:bind` as above. The phone never uses the admin JWT or sends its private key. CLI revocation uses `--admin-jwt-file PATH --revoke DEVICE_ID --reason lost|stolen|suspected_compromise|transfer|replacement|decommissioned|other`.

## Algorithm and policy

Convex default V8 runtime documents `SubtleCrypto`, but availability of Ed25519 across native platforms and the Convex production runtime is not established. This implementation deliberately standardizes on WebCrypto ECDSA P-256/SHA-256, with SPKI import and P1363 signatures, tested using generated real key pairs. Security/ADR-020 review must explicitly accept this algorithm before production (or amend the ADR); never silently downgrade to symmetric connector HMAC. Challenge TTL and proof skew are currently engineering values, not signed client policy. Challenge issuance requires an online bearer, and offline work remains provisional until reconnect/revocation check. Public challenge issuance needs abuse/rate limiting and eventual expired-challenge retention cleanup before production; neither makes an unbound bearer a device proof.
