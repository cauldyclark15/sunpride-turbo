# Mobile SFA HTTP contract v1 (slice A baseline)

**Status:** canonical shape for implementation, not a claim that routes, device proof, change-feed hooks, or native clients are shipped. Machine-readable envelopes and discriminated operation/activity payloads: [`packages/domain-contracts/schemas/mobile-v1.schema.json`](../../packages/domain-contracts/schemas/mobile-v1.schema.json). ADR-010/012/013/016/017/019/020/021 govern interpretation. No external integration ID is necessary for mobile execution.

## Transport and trust

`POST /mobile/v1/bootstrap`, `/mobile/v1/pull`, `/mobile/v1/push` over HTTPS with JSON. Every envelope has `type` and `contractVersion: 1`; every response includes integer UTC-epoch-ms `serverTime`. Request `deviceId` is an opaque server ID, **not authorization**. The server authenticates the short-lived user bearer **and** verifies device-key proof, nonce, app binding, active profile, current assignment, role, unit and device status on every request, before replay lookup. Exact proof headers/algorithm, HTTP status mapping and maximum byte sizes await the device-auth/HTTP implementation and security review; clients must not assume a shared secret or use the connector's authentication. The van POS is a separate application: this v1 field gateway does not accept sales, stock, payments or orders.

An absent optional property means _not supplied / unchanged_; explicit `null` means _known absent_ where the schema permits null. These are not interchangeable. Unknown request fields, variants and enum values are rejected (`invalid_request` or `version_unsupported`), never silently coerced. Clients must tolerate unknown **response** enum values by displaying an unknown state, retaining raw data safely and disabling transitions they cannot interpret; no guessed default, especially for financial or location states. A breaking field/removal/semantic change requires v2; additive response properties may be ignored by v1 clients after a documented compatible revision. Servers should continue v1 during the stated support window (to be decided), never silently reinterpret v1. JSON Schema is the structural contract; writers validate cross-record references, dates, numbers, sizes, ordering and capability server-side.

## Identifiers, dates, revisions

Server entity IDs (`id`, `visitId`, `deviceId`, `entityId`) are opaque strings, never parsed for scope or sequence. Client `clientVisitId`, `clientRequestId`, and `dependsOn` keys are stable 128-bit UUIDs (UUIDv7 preferred, random UUID when clock cannot be trusted), stored with the durable outbox and reused byte-for-byte on retry. Human codes are organization-scoped display/business keys and not relational grants. `outletId` is the physical visit target; `customerId` is an optional accounting link. A prospect without a link remains visitable but non-financial. Internal actors store the **full** issuer-and-subject `identity.tokenIdentifier` (`issuer|subject`), never the suffix alone or a client-provided employee ID; those values are not mobile DTO fields.

`YYYY-MM-DD` is a calendar day in **Asia/Manila** and must be a real date (not UTC date slicing). All instants (`deviceTime`, `serverTime`, lease expiry, event times) are UTC epoch milliseconds; windows are half-open `[from,to)`. Device time is evidence, while server receipt time determines ordering. The signed planned visit's service day and immutable plan/slot/version lineage govern eligibility; an unplanned visit needs an approved exception reason. `revision` is a positive server-assigned projection revision and `seq` is a strictly increasing server-issued feed position within an organization, not a client counter. A repeated operation returns its stored original ack/IDs/server time; changed payload or actor/device with the same `(organizationId, kind, clientRequestId)` conflicts.

## Bootstrap

`bootstrap.request`: `{type,contractVersion,deviceId,dayFrom?,pageCursor?,limit?}`. A first page chooses Manila today and bounded near-term horizon; a `pageCursor` continues the **same** server snapshot. `bootstrap.response` contains `permissions`, server-derived `employee` and `scope`, `appConfig` (offline/cache lease expiry and disabled order capture), `plannedVisits`, scoped `outlets`, linked `localCustomers`, `route`, `tasks`, `productCatalog`, `page`, `nextPageCursor` and `syncCursor`. Prices and promotions are **`unavailable`**, not legacy product `unitPrice`; do not enable order capture. The page limit is 1–100. `nextPageCursor: null` marks final page; `syncCursor: null` on nonfinal pages, a non-null starting delta cursor **only** when the complete snapshot has been paged. No silent truncation or nationwide fallback. Server-side authorization must filter before counting or paging.

## Delta pull

`pull.request`: `{type,contractVersion,deviceId,cursor,limit?}` (1–50). `pull.response`: `{type,contractVersion,serverTime,changes:[{seq,entity,id,revision,op:'upsert'|'tombstone',value?}],nextCursor,hasMore}`. `value` is omitted on tombstones; it must be an explicitly scoped projection (not a raw document, profile subject, GPS fix or credential). Upsert `value` is entity-specific and will be narrowed before route release. Cursors are opaque, MAC-protected, bound to protocol version/identity/device/scope and expiry; clients persist and return them unchanged. Snapshot reads establish a high-water mark and page that same snapshot; subsequent deltas cover later writes. Advance even across empty filtered pages when `hasMore`. Cursor tampering, expiry or role/assignment/route changes require `rebootstrap_required`, with no partial result. If any advertised source lacks complete feed tracking, mark it unavailable or force rebootstrap rather than claiming a complete delta.

## Ordered push

`push.request`: `{type,contractVersion,deviceId,operations:[...]}` with 1–20 ordered operations. Each has `kind`, UUID `clientRequestId`, optional earlier `dependsOn` UUIDs and typed `payload`. Supported kinds: `visit.checkIn` (`clientVisitId`, explicit nullable `plannedVisitId` and `location`, `outletId`, Manila `serviceDate`, `deviceTime`, `intents`), `visit.activity` (`visitId`, discriminated `activity`, `deviceTime`), `visit.checkOut` (`visitId`, `outcome`, explicit nullable `reasonCode`/`location`, `deviceTime`). Activity variants: `inventory_check`, `merchandising`, `price_check`, `promotion`, non-financial `order_intent`, `note`. Location carries coordinates/provider/accuracy/mock signal/fix time; **no client `withinGeofence` flag is accepted**. `task.complete` and `collection.record` are declared for compatibility but return per-item `unsupported_operation` until independently authorized domain writers/collection policy ship; a collection intent is not a payment or settlement. Unknown kinds never execute.

`push.response` returns ordered `results:[{kind,clientRequestId,status:'accepted'|'rejected'|'conflict',code?,ack?}]`; accepted ack contains `entityId`, `eventIds`, original `serverTime`. A denied dependency is not consumed as an idempotency key. Each accepted operation writes domain state, immutable execution event, change and durable replay result in one Convex transaction; the whole HTTP batch is **not** atomic. Retry each UUID unchanged after partial transport failure. Pending location evidence never automatically certifies a completed/productive visit or per diem. Raw evidence is stored separately from synced/audit projections, with independent scoped exception review and no self-approval.

## Errors and provisional policy

Top-level `error.response` has stable `{code,message,retryable,details?}`; no raw coordinates, subject, key material or foreign-unit metadata in errors. Codes: `rebootstrap_required`, `conflict`, `unsupported_operation`, `device_revoked`, `scope_changed`, `version_unsupported`, `unauthorized`, `invalid_request`, `invalid_cursor`, `dependency_missing`, `out_of_scope`, `evidence_pending_review`, `temporarily_unavailable`. Business rejection is a per-operation result, not a transport 500. `device_revoked` blocks all endpoints; `scope_changed`/`rebootstrap_required` invalidate cached cursor and require online reauthorization. Version unsupported is explicit; unknown response status must not be treated as accepted. HTTP mapping and diagnostic detail policy are pending slice F.

**PROVISIONAL, CONFIG-DRIVEN, pending client sign-off:** effective outlet check-in radius 75 m; maximum horizontal accuracy 50 m; maximum foreground fix age 60 s; offline device/cache lease 24 h. These values are _not schema constants_ or client entitlements. Policy version/source and effective pin/radius are stored with evidence; no GPS, mock or out-of-radius proof auto-awards actual/productive credit. Also provisional: location/media retention and legal hold, cursor TTL/key algorithm/limits, collection methods/precision, productivity checklist and per-diem decisions. The server remains the authority on reconnect; offline revocation cannot retroactively erase unreceived work.
