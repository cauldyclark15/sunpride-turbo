# CSV operation contracts

These are four **separate** operations, not interchangeable ways to set a balance. Product master and opening stock are implemented; the two operational CSV contracts below specify future adapters to existing inventory workflows, **not** live import endpoints or downloadable templates. A preview must validate against current server state without writing; commit must revalidate. All quantities are decimal displays of scaled `int64` **product base units** (scale 1,000, at most three decimals), never implicit case-to-each conversions. Non-base UOMs require an explicit rational conversion and are out of scope for these CSVs ([ADR-006](../decisions/ADR-006-PRODUCT-AND-UOM-BASELINE.md)). A location is the stock address and stock status partitions it; only `postMovement` changes balances ([ADR-003](../decisions/ADR-003-OPERATIONAL-INVENTORY-AUTHORITY.md), [ADR-007](../decisions/ADR-007-INVENTORY-LOCATION-SEMANTICS.md)).

## Product master upsert (implemented)

Use [`product-master.csv` and its validation rules](../runbooks/MASTER_DATA_IMPORTS.md#product-master): required `product_code,name,category,base_uom,tracking_mode`; optional `selling_uoms,barcode,allocation_policy,shelf_life_days,expiry_required,manufacture_date_required,minimum_remaining_shelf_life_days,external_id` (policy-dependent requirements apply). Stable row key is the normalized immutable `product_code`; UOM codes must resolve, and there is no stock location or movement effective time. Preview returns rows, would-create, would-update and row errors; the runbook lists error codes and re-upload behavior. Duplicate content is a no-op under the same file/run identity, with `<type>:<runKey>:<chunkIndex>` keys and server chunk hashes ([`shared.ts:96-122`](../../packages/backend/convex/imports/shared.ts)); commit skips invalid rows but writes valid rows per 100-row chunk ([`products.ts:579-728`](../../packages/backend/convex/imports/products.ts)). Admin national scope is required for preview and commit (`products.ts:557-578`, `products.ts:601-603`). No inventory movement or approval path applies. Out of scope: SKU renames, price management, SAP-authoritative catalog sync.

## Opening stock (implemented, cutover only)

Use [`opening-stock.csv` and its validation rules](../runbooks/MASTER_DATA_IMPORTS.md#opening-stock): required `product_code,location_code,quantity,source_reference`; `lot_number,manufactured_at,expires_at` are policy-dependent; `unit_cost_minor` is optional. Stable row key is normalized product + active location + normalized lot (or empty lot for non-lot products). Quantity is positive in product base units; location is explicit; dates are lot attributes, **not** a backdated movement time. Preview reports rows, accepted count, base-unit total and row errors. Same-file replay returns duplicate, while an already occupied product/lot/location fails `duplicate_stock`; see the runbook's error and re-upload sections. Every 100-row chunk is all-or-nothing and posts one `opening_balance` movement with `sourceType: "cutover"` ([`openingStock.ts:405-409`](../../packages/backend/convex/imports/openingStock.ts), `openingStock.ts:563-574`); same chunk-key/file-hash/server-chunk-hash discipline as above (`openingStock.ts:441-475`). Admin national scope is required (`openingStock.ts:381-403`, `openingStock.ts:428-429`). No operational adjustment approval is implied. Out of scope: correcting stock after cutover or overwriting a live balance.

## Stock addition / adjustment (contract; not implemented as CSV)

**Purpose.** Import an explicit signed **delta**, not an absolute balance. A positive delta adds stock; a negative delta removes it subject to available stock, exact lot and policy constraints. This is distinct from measuring a count. The adapter creates an adjustment request, then a different authorized person decides it; only approval posts an `inventory_adjustment` movement. Existing request fields and submitted status are in [`adjustments.ts:13-76`](../../packages/backend/convex/inventory/adjustments.ts); decision, sign-to-direction mapping, `postMovement`, and posted status are at `adjustments.ts:78-163`. One CSV file has one source reference, adjustment type, and reason code; each chunk is a separate approval unit; no row may directly mutate a balance.

Template header, in order:

`source_reference,line_key,adjustment_type,reason_code,product_code,location_code,stock_status,lot_number,quantity_delta,unit_cost_minor,note`

| Column             | Required       | Type                | Validation / meaning                                                                                                                                                              |
| ------------------ | -------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source_reference` | Yes            | Text                | Nonempty stable external document reference; identical across file. Used for provenance, not a substitute for run key.                                                            |
| `line_key`         | Yes            | Text                | Stable source line identifier, unique within `source_reference`; retain on retries.                                                                                               |
| `adjustment_type`  | Yes            | Text                | Same value across file; maps to existing request `adjustmentType`. Allowed client values are **Open question** below.                                                             |
| `reason_code`      | Yes            | Text                | Same value across file; maps to required adjustment `reasonCode`. Allowed values are **Open question** below.                                                                     |
| `product_code`     | Yes            | Code                | Trim/uppercase; resolve active product and active inventory policy.                                                                                                               |
| `location_code`    | Yes            | Code                | Trim/uppercase; resolve active authorized inventory location. No implicit warehouse or truck.                                                                                     |
| `stock_status`     | Yes            | Enum                | Existing status at that location (`available`, `quality_hold`, `quarantine`, `damaged`, `expired`, `rejected`, `wip`, `in_transit`); no implicit status.                          |
| `lot_number`       | If lot-tracked | Code                | Trim/uppercase; resolve an existing lot of the product. Required for tracked additions **and** removals; no silent lot creation or FEFO substitution. Empty for non-lot products. |
| `quantity_delta`   | Yes            | Signed decimal      | Nonzero, at most three fractional digits, product base UOM; `+` adds and `-` removes. Cannot drive balance negative.                                                              |
| `unit_cost_minor`  | No             | Nonnegative integer | Minor currency units per base UOM, if supplied; no guessed cost. Accounting treatment is **Open question** below.                                                                 |
| `note`             | No             | Text                | Audit context; not a reason-code replacement.                                                                                                                                     |

**Stable row key:** `(source_reference, line_key)`, unique across the whole file even if the same product/lot appears on multiple legitimate lines. Preserve the original row number for error reporting. Explicit `location_code` and `stock_status` select the partition; lot selects its exact allocation. No `effective_at` CSV column: request and approval times are server-recorded; movement `effectiveAt` defaults to approval posting time and `postedAt` is server commit time (`posting.ts:400-415`). Historical backdating is out of scope under ADR-003.

**Dry run:** return row count, accepted/invalid rows, positive and negative base-unit totals separately **by product base UOM and location/status** (never sum unlike UOMs), projected net delta and projected after-balance per product/location/status/lot, number of adjustment requests/movement chunks, any insufficient-stock or policy failures, and `{rowNumber,column,code,message}` errors. These are provisional: revalidate at request and again at approval against current balances; preview never reserves stock. A failed posting cannot silently become a partial approval.

**Row errors:** reuse `required_missing`, `invalid_format`, `unknown_reference`, `policy_missing`, `duplicate_in_file`, `scope_denied`, `too_many_rows` from [`shared.ts:36-47`](../../packages/backend/convex/imports/shared.ts). New proposed codes: `zero_delta` (signed delta is zero), `insufficient_stock` (negative delta exceeds eligible current stock), `lot_required` (tracked row lacks explicit lot), `approval_conflict` (balance/policy changed since preview or request), `invalid_reason` (reason/type not configured). Report all row errors with original row number; file-level authorization and replay-key conflicts may reject the request before row validation.

**Duplicate/replay and atomicity:** target the existing 5,000-row file / 100-row sequential chunk convention (`shared.ts:6-8,88-122`), with import type `stock_adjustment`, key `stock_adjustment:<runKey>:<chunkIndex>`, content `fileHash` grouping and **server** `chunkHash` including chunk rows and source reference. Same key/hash returns recorded result without another request or movement; same key with changed file/chunk hash rejects. Also detect the identical file hash for this operation under another run key and report duplicate rather than creating a second delta. This cross-key check is a requirement for the new adapter, not a claim of existing behavior. A chunk is one adjustment approval unit of at most 100 lines: validate the entire chunk and stage its request atomically, or reject it with no request; after a separate approval, `postMovement` and status/ledger/audit update atomically or nothing posts. Other chunks may have independent outcomes; **no file-wide transaction**. Never treat an earlier failed/staged chunk as posted on replay. No automatic retry with a new run key after a changed file without review.

**Authorization:** proposed capability `inventory.adjustment.request` for preview/request and `inventory.adjustment.approve` for posting, both checked against every target location's organizational scope; return `scope_denied` where safe. Current `request` only calls `requireIdentity` (`adjustments.ts:30-31`), while `decide` requires `admin`, `manager`, or `approver` and forbids self-approval (`adjustments.ts:86-96`). The CSV adapter **must add** location-scope checks; it must not imply that the current role gate already enforces them. Open question: mapping of these capability names and locations to actual roles/scopes.

**Out of scope:** opening balance, absolute quantity overwrite, count-derived variance, transfers/status moves, creating lots, SAP snapshots as corrections, unapproved posting, and arbitrary backdating.

## Cycle-count reconciliation (contract; not implemented as CSV)

**Purpose.** Record observed **absolute counted quantities**, compare them to a count session's frozen expected `systemBase`, and post **only nonzero variances after separate approval**. This is a physical count, not a direct adjustment CSV and not SAP snapshot reconciliation (`reconciliation.ts:6-94` reads SAP snapshots and writes differences, never stock). Existing `counts.start` creates a location-bound session and expected lines at a server `snapshotAt` (`counts.ts:8-84`); `counts.submit` computes `countedBase - systemBase` and marks submitted (`counts.ts:86-132`); `counts.approveAndPost` creates a `stock_count` adjustment, posts `inventory_adjustment` with `sourceType: "stock_count"` only for nonzero variances, and marks posted (`counts.ts:134-244`).

Template header, in order:

`count_reference,location_code,product_code,stock_status,lot_number,counted_quantity,finding,note`

| Column             | Required       | Type    | Validation / meaning                                                                                                                           |
| ------------------ | -------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `count_reference`  | Yes            | Text    | Existing count session's stable `countNumber`; resolve one session in `counting` state.                                                        |
| `location_code`    | Yes            | Code    | Active location; must equal session location and be within caller's scope. No inferred destination.                                            |
| `product_code`     | Yes            | Code    | Existing active product with inventory policy; must resolve to exactly one expected session line.                                              |
| `stock_status`     | Yes            | Enum    | Must equal expected line's status; current `counts.start` snapshots **`available` only**. Other statuses are out of scope until supported.     |
| `lot_number`       | If lot-tracked | Code    | Existing normalized lot identifier matching the expected session line; empty for non-lot products.                                             |
| `counted_quantity` | Yes            | Decimal | Absolute physical count ≥ 0, at most three fractional digits in product base UOM. **Zero is valid**; never enter a signed variance.            |
| `finding`          | No             | Enum    | Existing `over`, `missing`, `damaged`, `expired`, `wrong_lot`, `wrong_location` (`counts.ts:93-103`); explanatory only, not a status transfer. |
| `note`             | No             | Text    | Count evidence/context.                                                                                                                        |

**Stable row key:** `(count_reference, location_code, product_code, stock_status, normalized lot_number-or-empty)` must identify exactly one expected count line; duplicate keys, unknown lines and omitted expected lines block the session's submission (omitted does **not** mean zero). The session fixes location and `snapshotAt`; the observation is entered during the count, while the actual adjustment movement effective time is the server approval/post time (`posting.ts:400-415`), not `snapshotAt`. If inventory changed after the snapshot, do **not** apply a stale variance; require review/recount rather than overwriting live stock. No backdated CSV effective time.

**Dry run:** return count sessions/lines, valid/invalid/zero-variance counts, expected and counted base-unit totals **per product base UOM and location/status/lot**, signed variance totals split into gains/losses, projected eligible balance and proposed movement lines, snapshot time, and `{rowNumber,column,code,message}` errors. In blind-count sessions, do not reveal expected quantities or variance to the counter before submission; only an authorized approver receives those details. Recheck session, completeness and live balance before approval; no preview or submission posts stock.

**Row errors:** reuse `required_missing`, `invalid_format`, `unknown_reference`, `policy_missing`, `duplicate_in_file`, `scope_denied`, `too_many_rows`; `not_positive` does **not** apply because zero is valid. New proposed codes: `count_line_missing` (no expected line), `count_incomplete` (expected line omitted), `count_not_open` (session no longer counting), `stale_snapshot` (live stock changed since snapshot), `insufficient_stock` (approved loss cannot be posted), `approval_conflict` (session/line changed before approval). Errors retain source row numbers; file-level session/completeness errors can also identify the session reference.

**Duplicate/replay and atomicity:** target the same file hash, server chunk hash, 100-row chunk, 5,000-row limit and `<type>:<runKey>:<chunkIndex>` convention, with type `cycle_count`, including session reference(s) in chunk provenance. Same file and key returns duplicate without resubmitting/reposting; changed payload under a used key rejects; the identical file hash under another run key is a duplicate even if no movement resulted (new adapter requirement). A count session must not be split across chunks: validate all expected lines and submit one session atomically, then approve/post that session separately and atomically (zero-variance session posts no movement). Up to 100 count lines per CSV approval unit is the conservative limit under the current 100-line `postMovement` cap (`posting.ts:374-376`); reject an oversized session rather than partially post it. Other complete sessions/chunks may proceed independently; **no file-wide transaction**. Existing `counts.start` can create more lines than this, so larger-session chunking is **Open question** below, not an implemented path.

**Authorization:** proposed capability `inventory.count.submit` for preview/submission and `inventory.count.approve` for posting, each scoped to the session location. Existing start/submit only require identity (`counts.ts:20-22`, `counts.ts:108-110`); approval requires `admin`, `manager`, or `approver`, rejects self-approval by the session creator, and requires every line counted (`counts.ts:141-161`). CSV must enforce location scope and protect blind expected values; current functions are **not** a CSV scope gate. Open question: exact capability-to-role and location-scope mapping.

**Out of scope:** absolute balance overwrite, accepting missing rows as zero, inventing lines/lots not in the count snapshot, non-available statuses in the current session implementation, SAP comparison as an auto-correction, status transfers, arbitrary backdating, and approval by the counter.

## Open questions (client/product decisions; no assumed rules)

- **Open question:** Which `adjustment_type` and `reason_code` values are allowed for operational additions/removals and count approvals? Are reasons mandatory per document only or also per line? Current APIs accept strings, not a controlled catalog.
- **Open question:** Which approval thresholds, segregation rules beyond no self-approval, and escalation levels apply by quantity, value, location, or reason? No threshold is encoded in these contracts.
- **Open question:** Which roles/capabilities may preview, request, count, and approve for each warehouse/truck/organization scope? The existing identity/role checks do not implement per-location scope.
- **Open question:** Should a CSV adjustment's optional cost override be allowed, and what are valuation/closed-period/SAP consequences? The posting engine accepts a cost but ERP financial policy is not defined here.
- **Open question:** How should stale count snapshots be resolved (recount, refresh/rebase with explicit evidence), and how should sessions over 100 CSV rows be safely split or approved without breaking session-level completeness and atomicity?
- **Open question:** Which count types (`cycle`, `full`, `spot`, `route_close`) and blind-count disclosure policy are permitted for CSV by client operations? This contract describes cycle counts only.
