# Mobile SFA v1 compatibility policy

Canonical wire contract: [`mobile-v1.schema.json`](../../packages/domain-contracts/schemas/mobile-v1.schema.json), with TypeScript types/runtime validation in `packages/domain-contracts/src/index.ts`. The Swift/Kotlin files under `fixtures/mobile-v1/` are **contract text fixtures**, not compiled native clients. Tests validate positive envelopes, negative unknown-enum responses, native field/enum inventory, nullability and required-field failures; `test/mobile-v1-baseline.json` freezes every required path and enum value against in-place schema drift. Do not maintain independent enum mirrors in web/mobile code. `MOBILE_SFA_V1.md` supplies policy beyond structural JSON Schema; `MOBILE_AUTH_V1.md` supplies bearer/device proof. The package is wired into root Turbo lint/typecheck/test.

## v1 wire rules

- `contractVersion: 1` and the `type` discriminator are required. Requests are strict: unknown fields, operation kinds, enum values or version fail, never coerced. Top-level errors have stable `code`, safe message, retryable flag and server UTC-epoch-ms `serverTime`; operation rejection is an ordered push result rather than a transport success claim. Authentication must run before replay lookup.
- Responses may add optional fields without changing existing meanings; consumers should ignore unrecognized _response_ properties while preserving safe raw values. **Current v1 JSON Schema uses `additionalProperties: false`**, so this requires an explicit schema-compatible revision and updated fixture/validator tests before shipping; the current TypeScript runtime validator correctly rejects such a field until then. Unknown response enum values can appear from a future server: decode as `{unknown: raw}` with `decodeResponseEnum` and disable transitions. The strict v1 envelope parser rejects an unknown response enum; a client needing forward-read should decode an unknown status separately rather than coerce it into a known accepted state. Do not substitute `accepted` for an unknown value.
- Missing optional property means not supplied; explicit `null` means known absent **only where allowed**. `plannedVisitId`, `location`, `reasonCode`, `route`, `nextPageCursor`, `syncCursor` illustrate explicit nullable fields; do not serialize them as omitted when required. Bootstrap `syncCursor` is null until the final page; no partial starting cursor. Pull requires a bounded `limit` in the schema even though prose describes it as optional: callers must send it until a deliberate v1 schema revision.
- IDs are opaque, UUIDs for durable client operation keys, day-only dates use Asia/Manila, UTC epoch milliseconds for instants, server-assigned revisions/sequences and opaque scope-bound cursors. Neither server IDs nor client device IDs grant access. Offline operation replay preserves the original acknowledged server IDs/time. Price/promotion remain `unavailable`, and this gateway does not authorize order/stock/payment operations.

## Breaking-change gate

Removing or renaming a required property; turning optional into required; changing nullable to non-nullable; changing a discriminator, enum, code, ID meaning, clock unit, date zone, authorization rule, idempotency scope, cursor meaning or response envelope; narrowing ranges or silently repurposing a value is **breaking**. Adding a required request property or a new request variant that old servers might interpret incorrectly is also breaking. Additive optional response fields require a declared compatible v1 revision and tests proving old clients can ignore them; expanding response enums requires unknown-state safety, not guessed fallback. Test both old fixtures and representative new ones against the old and new consumer behavior; serialize platform fixtures, not just compile types. Changes to server-side restrictions may require operational coordination even when JSON remains structurally identical.

To ship v2, create a **new** `mobile-v2.schema.json`, separate TS models, Swift/Kotlin fixtures and v2 tests; register explicit `/mobile/v2/{bootstrap,pull,push}` routes and version error mapping. Keep `/mobile/v1/*` on its original semantics through a published support/migration window (**not yet agreed**); do not auto-upgrade a v1 cursor or silently reinterpret an old outbox UUID. First sync v2 with a fresh authenticated bootstrap and cursor, drain/reconcile v1 outbox with original keys, then cut over per device. Write bidirectional compatibility tests and release notes, measure active v1 devices and plan rollback before retiring v1. Native deployment and real-device serialization are separate acceptance gates; these text artifacts alone do not prove them.
